## 一、背景与目标人群

目标人群：有炒股或投资理财需求的普通用户（含大量非技术用户，不会命令行，只用自然语言与自己的 AI agent 对话）。

核心洞察：这类用户想要的是"告诉 agent 我要什么数据，它每天帮我整理好"，而不是学一套工具。因此本产品的所有交互都通过**用户与自己的 agent 自然语言对话**完成，skill 是装在用户 agent 上的能力包。

## 二、产品形态

两个（未来三个）可组合的 agent skill + 一份边界契约，开源发布，与具体 agent 环境无关（Kimi Code / Claude Code / workbuddy 等均可加载）。

- **stock-field-registry（Skill 1）**：信息定义与口径规范
- **stock-data-collector（Skill 2）**：数据自动采集与落库
- **stock-notifier（Skill 3，规划中）**：场景化条件通知

## 三、Skill 1：信息定义与口径规范（已实现）

用户用自然语言表达的需求是模糊的（"我要北向资金"有 5 种口径）。Skill 1 把模糊需求变成精确的、经过实测验证的字段定义。

**核心流程**：

1. **Step 0 字段清单输入与匹配**：输入可以是文字描述，也可以是 agent 从附件（如 Excel 表头）解析出的字段名列表。逐字段匹配：命中 registry 已有字段 / 疑似同义（带选项问用户）/ 全新字段
2. **Step 1 口径消歧**：不空手反问，带着调研结果和选项问用户
3. **Step 2 信源验证**：6 项必验（能取到/单位/语义交叉/更新节奏/历史回溯/边界行为），用 probe_source.py 实跑取证
4. **Step 3 产出 registry 条目**：schema 2.0，含**可执行声明**（fetcher+params 或 computed.function）、证据（样本值、交叉验证记录）、状态机（draft→verified→production→deprecated）

**交付物**：`registry.json`（机器契约，单一事实源）+ 人读《字段说明表》（render_registry.py 自动生成，永不手工维护）。

**内置字段库（field_library.json）**：Skill 1 自带一份共识字段库（当前 15 个字段：口径 + 信源 + 证据，全部实测验证）。定位：

- **用户双路径**：既可以从字段库里直接勾选要用的字段，也可以用自然语言描述新字段（走 Step 0-3 调研流程）；两条路径的产物格式完全一致
- **变体建模**：同名字段的不同口径是不同的库条目，用 field_id 区分（如 `pe_static`（已废弃）vs `pe_ttm`；未来 `macd_daily`（不复权）vs `macd_daily_qfq`（前复权））。库条目口径注明"可经变更流程切换变体"
- **用时再验证**：库条目附带验证日期与证据，但每次真实接入时仍按 Ready 契约重新核查（信源可能已变化），不盲目信任库存证据
- **持续生长**：每次为用户调研的新字段，验证达标后回流字段库（开源后通过 PR 回流），库越用越全。废弃条目标记 deprecated 保留，不删除（口径史可追溯）

**已定稿口径示例**：MACD=平安证券·不复权（含东财 fqt=0 锚点验证证据，见 field-standards.md）。口径是 Skill 1 的可变决策：用户要前复权/其他口径时走变更流程（新版本→用户决策→Skill 2 重新接入），Skill 2 零代码改动。

**关键原则**：不编造——没有可靠信源就如实告知并推荐替代品；证据必须实测。

## 四、Skill 2：数据自动采集（已实现）

**字段执行器架构**：采集行为完全由 config（registry 快照）中的字段定义驱动——采集型按 `fetcher`+`params` 走信源插件，计算型按 `computed.function` 走公式注册表，列布局按 `layout` 声明。**新增字段零代码**（已支持信源族与公式范围内）。新信源族 = 加一个 fetcher 插件文件；新公式 = 注册一个函数。

**已实现能力**：

- 信源插件 6 个：腾讯K线、腾讯实时、新浪实时、东财实时、东财K线、搜狐K线（历史备胎）
- 公式注册表 6 个：identity / diff / pct_change / amplitude / pe_static / macd（日/周/月）
- 主备源自动切换；单源故障留空+告警，绝不编造
- 按 registry 定义执行 MACD 日/周/月计算（当前种子口径=平安证券·不复权，可经 Skill 1 口径变更切换复权方式）；月线 EMA 全历史收敛（搜狐前补执行机制）
- 存储适配层：CSV（默认零依赖，Excel 直接打开）/ 腾讯文档（tdoc，待实测）；钉钉文档/飞书在适配层设计上可插拔扩展
- 批量补录 `--days N`、单点补录 `--date`、幂等防重、`--dry-run` 试跑
- 完整性核查 check_integrity：日期连续性、收盘价一致性、字段级 non_null/range/cross_recompute，`--fix` 重算回写
- 异常守卫：无效代码拒接、退市/长期停牌拒接（--force 可强制）

**交付物**：per-stock `config.json`（完整可执行快照 + layout + storage 配置）+ 每日数据（CSV/在线文档）+ 完整性核查报告。

**采集频次定位（决策 2026-08-19）**：正式需求 = 每日/每周（收盘后）。分钟级高频采集为**远期脑洞**，不进当前架构（盘中实时流是不同信源与存储量级，需要时单独立项）。

## 五、Skill 3：场景化条件通知（规划中，先发布再补）

监控 Skill 2 采集的数据（原始值或二次计算值），触发用户预设条件时主动通知。

**设计草案**：

- 触发条件示例：MACD 金叉/死叉（数据现成）、涨跌幅超阈值、换手率异常、价格突破
- 条件定义归属：沿用"知识归 Skill 1、执行归 Skill 2"的边界思想，条件规则存 per-stock config
- 通知通道：钉钉（机器人/DING，dws CLI 已打通）、邮件；可插拔扩展
- 运行方式：每日采集完成后由定时任务顺带检查，非实时监控

**决策（2026-08-19）**：先完成 Skill 1/2 开源发布，Skill 3 作为发布后第一个大版本迭代。

## 六、边界契约（核心设计原则）

两个 skill 的协作模型：**目录 + 快照**。

- Skill 1 产出 registry（字段权威定义，纯知识产物）
- Skill 2 接入时读一次、拷贝进 per-stock config（完整可执行快照，带版本戳）
- **运行时零耦合**：每日采集只读 config，registry 删了都不影响当天采集
- **registry 更新不自动传播**：加字段是显式的重新接入（人工触发）
- 灰色地带归属：知识（口径/信源/方法）归 Skill 1，数据（落库值/运行状态/告警）归 Skill 2；两 skill 不互相调用，用户是总线

详见仓库 BOUNDARY.md（单一事实源）。

## 七、规范分层原则（L1/L2/L3）

本文档及本项目所有"规范"按消费方分层，不同层次给 AI 的自由度不同：

| 层次 | 定义 | 规范力度 | 例子 |
|---|---|---|---|
| **L1 机器契约** | 会被脚本或另一个 skill programmatically 消费的定义 | **写死，不许偏离** | registry schema、field_id 命名、单位、fetcher/params、computed 函数名单、config 结构 |
| **L2 协作接口** | 多个流程/时间点之间需要有共同预期的格式 | **给默认模板 + 显式注明"可按场景调整"** | 口径表表头、定时任务 prompt 模板、字段说明表结构 |
| **L3 呈现层** | 只影响当下阅读体验的表达 | **只给示例，完全放权** | 给用户的话术、表格样式、欢迎语措辞 |

判断标准：这个细节会被"谁"消费？影响另一个工件/脚本 → L1 写死；影响协作预期 → L2 默认值；只影响阅读体验 → L3 放权。

**口径表默认表头（L2 示例）**：

```
字段 | 口径定义 | 单位 | 主力源 | 备用源 | 更新节奏 | 历史回填 | 状态
（视图层默认值。agent 可根据用户场景增删列；若被其他流程引用，以此为准）
```

本项目架构本身就是这一原则的体现：registry.json 是严格 schema（L1），字段说明表只是 render 出来的视图（L2/L3）。

## 八、开箱体验与验收体系

**开箱即用**：用户只给一个股票代码即可试跑——onboard 缺省回退到内置演示字段集（15 个预装字段：行情 12 字段 + MACD 日/周/月，全部实测验证达标）。

**首次使用引导**（写进 SKILL.md）：欢迎介绍 → 必问数据存放位置 → 快速出活并表格化展示（aha 时刻）→ 引导设置每日自动更新。

**验收体系**：

- `verify_demo.sh`：8 步自动化验收（编译→onboard→dry-run→写入→补录→核查→篡改修复→渲染），每轮迭代的固定验收载体
- `TESTING.md`：小白剧本（A 主线 7 步 + B 刁难 14 场景），用于真实用户测试
- 干净会话端到端验证：零上下文新 agent 仅凭文档独立完成全旅程（已实测通过）
